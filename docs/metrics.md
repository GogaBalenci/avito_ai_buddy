# Метрики пользы и проверка эффекта

Что считаем, откуда берём цифры и как на пилоте отличить пользу бадди от случайности. Все метрики считаются из событий прототипа: таблица `app.events` (без текста сообщений и ПДн) и `app.path_period_stats`. Большая часть уже видна на дашборде Grafana (`docker compose --profile observability up -d`, <http://localhost:8381>). Базовых цифр Авито у нас нет: целевые значения ниже — **допущения команды**, их уточняют на пилоте.

## 1. Главная метрика — для стажёра

**Доля стажёров, закрывших неделю 1 вовремя** (все свои шаги этапа «Неделя 1 — Вход в команду» отмечены «Готово» до 7-го дня от старта).

Почему она: первая неделя — это каналы, доступы и знакомство, то есть ровно те оргдействия и вопросы, которые бадди снимает с наставника. Если стажёр закрывает её вовремя, он раньше переходит к задачам команды. Метрика не зависит от того, нравится ли стажёру чат: её двигают выполненные шаги.

| | |
|---|---|
| Источник | событие `step_done` (`on_time`, `day`, `period`), снимок `app.path_period_stats` |
| Как считаем | стажёры когорты, у которых все шаги `week1` в статусе `done` и последний `step_done` по `week1` пришёл с `on_time = true` / все стажёры когорты |
| На дашборде | таблица «Неделя 1: прогресс стажёров» |
| Цель пилота (допущение) | +20 п. п. к контрольной группе |

Защита от «накрутки галочками»: шаги с заявкой (`help.kind = access_request`) стажёр не может отметить сам — их закрывает только статус заявки из сервиса доступов (`13`, разрешение `buddy.path.sync` только у роли `system`). Дополнительно сравниваем с метрикой из трекера задач (п. 2).

## 2. Вспомогательные метрики стажёра

| Метрика | Источник | Зачем |
|---|---|---|
| Время прохождения шагов (медиана дней от `period_started` до `step_done` по этапу) | `period_started`, `step_done` | Где стажёры застревают — сигнал для владельцев трека |
| Время до первой самостоятельной задачи | трекер задач (на пилоте; в прототипе нет) | Проверка, что «вовремя закрытая неделя» действительно ускоряет выход на задачи |
| Доля действий, доведённых до результата | `action_drafted` → `action_completed` (воронка) | Удобство отгула и заявок: где бросают |
| Ошибки в датах отгула | `time_off_validation_failed` | Понятность формы |

## 3. Метрика для наставника — сэкономленные часы

По кейсу наставник тратит **40–48 ч** за 6-месячную программу и **55–65 ч** за 9-месячную. Считаем, сколько из этого берёт на себя бадди:

```
часы = (вопросы без эскалации × T₁ + оргдействия через бадди × T₂) / 60
```

- **вопросы без эскалации** — `question_answered`, после которых в той же сессии не было `escalated` и `feedback = down`;
- **оргдействия через бадди** — `action_completed` (отгул, заявка на доступ);
- **T₁, T₂** — среднее время наставника на ответ и на оргдействие, минуты. Допущение команды: T₁ = 5 мин, T₂ = 10 мин; на пилоте спрашиваем наставников.

| | |
|---|---|
| Доля вопросов, решённых без наставника | 1 − `escalated` / (`question_answered` + `escalated`) |
| Эскалации по причинам | `escalated.reason` — на дашборде «Эскалации к наставнику по причинам» |
| Цель пилота (допущение) | −25% времени наставника на оргвопросы в первый месяц |

## 4. Качество ответов

| Метрика | Источник |
|---|---|
| Оценки «Помогло» / «Не то» | `feedback` (дашборд «Оценки ответов») |
| Расхождения в инструкциях, найденные стажёрами | `doc_conflict_reported` — уходят владельцам документов |
| Отказы по правам | `permission_denied` (дашборд «Отказы по правам») — нет ли ложных отказов |
| CSAT после недели 1 | опрос на пилоте (в прототипе нет) |

## 5. Надёжность

| Метрика | Источник | Порог |
|---|---|---|
| p50 / p95 времени ответа | `reply_sent.latency_ms_total` | локальные операции < 1 с; с моделью p95 < 5 с |
| Доля ответов с моделью и в упрощённом режиме | `reply_sent.mode` (`demo` / `llm` / `fallback`) | `fallback` < 5% при включённой модели |
| Откаты модели по причинам | `llm_fallback.reason` | — |

## 6. Как проверить эффект — план пилота

1. **Группы.** Одна когорта стажёров (например, весенний набор) делится случайно пополам внутри каждого направления: у опытной группы включён бадди, у контрольной — обычный чек-лист и наставник. Включение — через feature flag по `user_id` (в прототипе флаги уже читаются на каждом запросе через `FlagProvider`; флаг когорты добавляется так же).
2. **Срок.** Первые 4 недели стажировки (этапы «Неделя 1», «Неделя 2», «Недели 3–4»); главная метрика снимается на 8-й день.
3. **Что считаем успехом.** Главная метрика лучше контрольной на ≥ 20 п. п. **и** время до первой самостоятельной задачи не хуже. Если растут только «галочки», а задачи не ускоряются — бадди не помогает, а мешает.
4. **Что ещё смотрим.** Часы наставника (опрос + формула выше), оценки ответов, доля `fallback`.
5. **Ограничения.** Маленькая когорта даёт большой разброс: решения принимаем по двум когортам подряд. Наставники в обеих группах одни и те же — возможен перенос привычек, это фиксируем в итогах.

## 7. Пример запроса

Доля ответов с моделью и p95 за последние 7 дней:

```sql
SELECT mode,
       count(*) AS replies,
       percentile_cont(0.95) WITHIN GROUP (ORDER BY (payload->>'latency_ms_total')::numeric) AS p95_ms
FROM app.events
WHERE name = 'reply_sent' AND ts > now() - interval '7 days'
GROUP BY mode;
```

Неделя 1 вовремя по стажёрам (то же, что на дашборде):

```sql
SELECT user_id, done, total, round(100.0 * done / nullif(total, 0)) AS pct
FROM app.path_period_stats
WHERE period = 'week1'
ORDER BY pct DESC;
```

# Design: add-access-requests

Полное описание — `docs/11-spec-s1-s2-s4.md` v1.2, раздел 3 (§3.5–§3.14).

## Правила имитации (§3.5)
- `auto` — `approved` сразу; `mentor` — ждёт решения наставника; `timer` — `approved` при первом чтении не раньше `created_at + ACCESS_TIMER_MINUTES` (без фоновых задач, условный `UPDATE`).
- Флаг `access_mentor_approval = off` (хранится в `mock_admin.flags`) превращает `mentor` в `timer` — режим черты отсечения без экрана наставника.
- `approver` — только подпись; решение принимает правило. Обоснование — «Шаг {{ref}} чек-листа адаптации: {{title}}» или «Запрос из чата бадди», свободного текста нет.

## Распознавание ресурса (§3.5.4)
Алиас — сущность; намерение `access_request` только вместе с глаголом доступа. Алиасы конкретные (загрузчик отклоняет одиночные «каналы», «чат»).

## Синхронизация (§3.6)
`list_requests` (заодно применяет таймер) → для изменившихся заявок сначала `checklist.set_step_status` от `system` (идемпотентно), затем условный `UPDATE` локальной копии → событие `access_request_decided` ровно один раз. Ошибка → повтор на следующем чтении. Фронт опрашивает только при `has_pending_requests` и в активной вкладке.

## MCP `access` (§3.10)
`create_request` идемпотентен по ключу, `DUPLICATE_ACTIVE` при активной заявке (плюс частичный уникальный индекс); `decide_request` — только наставник и только свои стажёры, `ALREADY_DECIDED` при гонке с таймером. Ответы — `RequestView` (`12` §6).

## Риски
- Таймер 2 мин долго показывать в видео — в видео правило `auto` и одобрение наставником, таймер — в README.
- Синхронизация в `GET /api/path` добавляет MCP-вызов; в проде — вебхук сервиса доступов.
